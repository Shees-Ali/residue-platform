## 2026-10-13 - Monorepo with three projects
web/ (React), api/ (FastAPI), voice/ (ADK) plus deploy/, seed/, memory/. Reason: one repo lets Pydantic models drive the OpenAPI spec and the typed web client; matches the plan.

## 2026-10-13 - Voice service never touches the database
voice/ calls the API over HTTPS with a Google ID token and imports no Firestore or DB client. Enforced by `scripts/check_no_db_in_voice.py` in CI. Reason: the API alone decides whether money moves.

## 2026-10-13 - Agent routes expose four tools only; identity comes from the call record
`/api/agent/*` has create lot, get quote, escalate, record confirmation. Request models carry a `call_id` and never a farmer id; the API resolves the farmer from the call record. Writes require an `Idempotency-Key` header. Reason: the model controls request fields, so it must not control identity.

## 2026-10-13 - Plan says quote_price, scaffold prompt says get_quote
Used `get_quote` (scaffold prompt wins; it is the later, more specific instruction). Rename later if desired.

## 2026-10-13 - Tests-first uses a `tdd` pytest marker
The failing tests for revenue_share, ledger check, offer expiry and factory scoring are marked `tdd`. CI runs `-m "not tdd"` as the blocking gate and `-m tdd` as a non-blocking job. Reason: a red baseline hides real regressions. Remove the marker per module when its implementation lands. Rejected: xfail (silently passes when fixed unnoticed).

## 2026-10-13 - Money as integer minor units, shares as basis points
Revenue split and ledger use integers (paisa, bps) so splits sum to exactly 10000 bps. Rejected: floats.

## 2026-10-13 - Stories not marked test-first for UI and voice

## 2026-10-14 - Primary store is Postgres (Cloud SQL), not Firestore
Data is relational (ledger invariants, offer ladder, four-way split, traceability), so the system of record moves to PostgreSQL. Local dev uses a Docker Postgres; Cloud SQL for Postgres at deploy time (GCP trial/billing sorted later). The API (FastAPI) is the only DB client and talks to it directly with SQLAlchemy 2 async + asyncpg, migrations with Alembic. `voice/` still never touches a database. Supersedes the "Firestore as the database" parts of `implementation-plan.md` (stack, components, running-free tables, ten-collections list). Firestore stays only for the events feed (next entry). Rejected: staying on Firestore (no FKs, awkward aggregates, integrity only in code); Firebase Data Connect (extra GraphQL layer, unclear Python server support, predefined operations make T1/settlement transactions harder, needs emulator; its generated web SDK is unused because the web reads through the API's OpenAPI client).

## 2026-10-14 - Tiny Firestore `events` collection as a refetch signal
After a Postgres commit the API writes one small doc to Firestore `events` (`{type, job_id?, at}`; no money, no personal data). Dashboards listen to it and refetch from the API. Only the API writes; signed-in users read. Replaces the live listeners on real data that the plan assumed (T1, A2, dashboards). Fallback if it is not ready: poll the API every 2-3 s. Event write failures must never fail the request (Postgres is the truth).

## 2026-10-14 - Postgres schema conventions
Money is `BIGINT` minor units with `CHECK (>= 0)`; shares are `INTEGER` bps. Statuses are `TEXT` with `CHECK (... IN (...))` (not native enums, so adding a state is a plain migration). Keys are `UUID` (server default `gen_random_uuid()`), except `users.uid` which is the Firebase uid. `timestamptz` everywhere. `ledger_entries` is append-only. T1's single winner is an atomic `UPDATE ... WHERE status='pending'` (zero rows = lost). Naming: column is `amount` (minor units); the existing `amount_cents` field in `app/models/ledger.py` is to be renamed. See `data-model.md`.

Docker is not required, keeping "only Python and Node" true. Until the Google Cloud trial is running (expected within ~2 days), a free external Postgres (e.g. Neon) is the dev/demo database; then move to Cloud SQL so the demo uses Google products only. No code change between them, only `DATABASE_URL`. Rejected: Postgres in a Cloud Run container (stateless, scales to zero, data lost); a Compute Engine e2-micro VM (ops burden, VPC access). Free-tier limits change; verify before relying on them.

## 2026-10-14 - F1: structured pickup window, recoverable errors, village matching
The model sends `pickup_date` (YYYY-MM-DD) and `pickup_part` (morning|afternoon|evening); the API converts to `pickup_from/to` in Pakistan time (fixed UTC+5). Invalid input returns 422 `{error, message, valid}` (handled by an exception handler for `LotError`), so the agent can ask again. Village: exact match in the district, then fuzzy (difflib 0.8), else the district centroid with `place_match="district"`; unknown district is a 422. Replaces the free-text `pickup_window` string. ## 2026-10-14 - Auth split: voice-service auth in F1, dashboard auth later

Voice has the matching `API_AUTH_DISABLED`.

## 2026-10-14 - Idempotency: stored responses, same transaction as the work
`run_idempotent` inserts the key row in the same transaction as the write and stores the response on success, so a failure rolls both back and a retry with the same key works; a replay returns the original body; same key with a different payload or route is 409; a request still in flight is 409. Concurrent duplicates wait on the unique key then replay.

## 2026-10-14 - Settings read the environment when built, not at import (voice)
`voice/app/config.py` uses `default_factory`, so flags like `API_AUTH_DISABLED` can be changed per process or per test. The API keeps import-time fields for now, with `auth_bypass_active()` reading env live.

## 2026-10-14 - Money model for jobs (assumed; configurable)
Shares of gross (weight x quoted price, integer paisa, half-up): farmer 7000 bps (fixed on the job at creation, it is what was quoted), transporter 2000 (`SHARE_TRANSPORTER_BPS`), platform 1000 (the remainder). Parts come from `revenue_share.split` so they sum exactly. Escrow is funded at the estimated weight; at confirmation it is topped up (`escrow_in`) or the difference returned (`refund`) to match the weighbridge weight. All of it lives in `app/services/economics.py` and is shared by quote, offers, funding and settlement so they cannot disagree. Rejected: per-tonne-km transport pricing (more inputs, no data for it).

## 2026-10-14 - Who is paid when
Transporter is paid at factory confirmation (matches T2 "released once the factory confirms"). Farmer share and platform fee are released when the farmer says yes on the verification call. A farmer "no" freezes the rest in escrow (`disputed`) and adds an admin escalation. A factory rejection pays the transporter their estimated share, refunds the rest, farmer gets nothing, lot becomes `rejected` (the "pre-agreed cost rule"). The `verified` state is unused: `verified_at` is stamped when the job goes `confirmed -> settled`.

## 2026-10-14 - Dashboard auth: role from the users table
Firebase ID token proves identity; the role comes from `users` (not custom claims), ownership from `factories.user_uid` / `transporters.user_uid`. Local bypass (`AUTH_DISABLED`, ignored when `K_SERVICE` is set) uses the `X-Dev-Uid` header to act as a seeded user. Seeded users: `dev-admin`, `dev-factory-N`, `dev-transporter-N`, `dev-buyer-0`.

## 2026-10-14 - Assignment runs inside create_lot; factory score is net delivered price
`assign_lot` runs in the same transaction as the lot insert, so a lot always has its ranking and job or stays `open`. Score = factory price minus haversine distance x 2,500 paisa per tonne-km (assumed cost). Admin override needs a reason, only before funding, and is stored on the chosen candidate row.

## 2026-10-14 - Dispatch is SQL-guarded; the tick also sends waiting jobs
One offer at a time (`OFFER_TTL_SECONDS`, default 120). Accept is one conditional UPDATE (pending, mine, not expired) followed by a guarded job transition, so concurrent accepts have one winner (verified with two real connections). The tick expires lapsed offers (rows locked with SKIP LOCKED), offers the next nearest eligible transporter, and sends funded jobs that never got an offer; an exhausted ladder returns the job to `funded` with `offers_exhausted`. `force` (expire everything now) is admin-only; Cloud Scheduler is recognised by `SCHEDULER_SERVICE_ACCOUNT`. Admin can `redispatch` and approve or revoke transporters (tier 1/2/3 = 3/7/15 t).

## 2026-10-14 - Sale split and ledger kinds for the marketplace
Product sales split farmer 5000, factory 3000, NGO 500, platform 1500 bps (`SALE_SHARE_*_BPS`; from the test shares in the plan). Migration 0004 adds ledger kinds `release_factory` and `release_ngo`. The farmers' share of a sale is pooled (no per-farmer attribution) and the NGO is a label. Stock is decremented by one conditional UPDATE, so the last unit cannot be sold twice.

## 2026-10-14 - Photo storage and grading behind interfaces
`Storage` (Cloud Storage when `STORAGE_BUCKET` is set, in-memory otherwise) and `Grader` (Gemini when `GEMINI_API_KEY` is set, else 503) are FastAPI dependencies so tests use fakes. Photo paths must sit under `jobs/{job_id}/{kind}/`. Grading uses whichever recent photos are readable. Neither real client has been exercised against Google yet.
## 2026-10-15 - Web Phase 1: domain layer in TypeScript, mirroring the API contracts
The demo's business logic now lives in a pure, React-free TypeScript domain (`web/src/lib/domain/`): `types.ts`, the state machine (`stateMachine.ts`), the reducer (`engine.ts`), the seed (`seed.ts`), and the four mandated pure functions `assignment.ts` (haversine + factory scoring), `dispatch.ts` (offer expiry + transporter ladder), `ledger.ts` (escrow invariant), `revenueShare.ts` (largest-remainder split). Rejected: swapping screens to the API now (endpoints are still 501).


## 2026-10-15 - Auth and roles: self-signup, admin approval, farmer role
Sign-in is Firebase Auth (Google and email/password). A new person signs in, then picks a role with `POST /api/me/register`: farmer and buyer are active at once; transporter and factory are `pending` until an admin approves (`/api/users/{uid}/approve`); `admin` is never self-selected and comes only from `BOOTSTRAP_ADMIN_EMAILS` with a verified email. Roles and status live in `users` (migration 0005: `farmer` role, `status` active|pending|suspended, `email`, `farmers.user_uid`). A pending or suspended account gets 403 `{code: pending_approval|suspended}` on every gated route; `/api/me` still answers so the web app can show the waiting page. A pending factory is skipped by `load_factories`; suspending a transporter clears `approved_at`, so dispatch stops offering them jobs. Supersedes the web rule "roles come from Firebase ID token claims": the role always comes from the `users` table through `GET /api/me`.
Rejected: self-chosen roles without approval for transporters and factories (they move money); roles as Firebase custom claims (needs a token refresh after every approval and a second source of truth).

## 2026-10-15 - Farmers prove their phone through Firebase, not by typing it
A farmer record is linked to a login only through the `phone_number` claim on the Firebase token (the web signup links a phone credential with an SMS code). The phone typed in the body is ignored for farmers. Without a verified phone the account is a farmer who sees nothing (`farmer_linked: false`), so nobody can read another farmer lots by guessing a number. One farmer row links to one login; a second signup with the same phone is 409. Farmers read their own lots (`GET /api/lots`, `/{id}`) and payouts (`GET /api/ledger/mine`, pending = quoted estimate until the job settles); no farmer writes exist, the voice agent still creates lots on their behalf. Firebase phone auth beyond test numbers needs billing: use test numbers for the demo.

## 2026-10-15 - Web state: Query for server data, context for auth, toasts for every error
Server data goes through TanStack Query (`web/src/api/query.ts`, `QueryProvider`): `unwrap(api.GET(...))` throws an `ApiError` with a readable message; one `QueryClient` toasts every failed query or mutation (opt out with `meta: { silent: true }`), retries a flaky network once and never retries a 4xx. Account state stays in `AuthProvider` (it is not server data and drives routing). Errors reach people as toasts (`components/ui/toast.tsx`): Firebase and Google sign-in errors, refusals from `/api/me/register`, and a failed `/api/me` load (a 401 also signs the person out, so the reason is toasted first). Rejected: Redux or Zustand (no client-only shared state yet); inline error paragraphs on the auth forms (replaced by toasts). ## 2026-10-15 - Validation first: one rule, one error shape, both sides
Rule (AGENTS.md): before any endpoint, form or field is built, its constraints, messages and feedback are written in the story file and `memory/validation-rules.md` and confirmed by the user; then the same rule is enforced on the API and mirrored on the web, with tests on both. The API answers every validation failure as `{detail, errors:[{field, message, code}]}` (422 bad input, 409 conflict): `app/validation.py` turns Pydantic errors into sentences that name the field and the rule, and `FieldErrors` carries rules that depend on data (unknown district with the valid list, phone or email already taken). Shared types: `Phone` (cleans to E.164, `03xx` becomes `+92`), `text(min, max)` (trimmed). Registration reports every missing or wrong field at once and rolls back the half-made account. The web mirrors the rules in `src/lib/validation.ts` (same wording), shows them under each input (`<Field>`), marks and focuses the first bad field, toasts a one-line summary, shows a spinner on the submit button, and maps API `errors` back onto the same fields (`ApiError.fields`). Tightened existing fields: names 2-80, phones E.164, factory price PKR 1 to 1,000,000 per tonne, 1-10 distinct residues, tier 1-3, status and role filters, override reason 3-500, escalation text caps; new confirm-password and an 8-character letter-and-number rule at signup. Open: Pakistani-only phone numbers; Firebase itself still allows 6-character passwords.

## 2026-10-16 - Phone input with country rules; one reCAPTCHA for every send
Phones are validated as real mobile numbers for their own country: `libphonenumber-js/mobile` on the web, the `phonenumbers` package in the API, both keeping only digits and a leading plus (so copied numbers with invisible direction marks work) and requiring a country code (a plus, 00, or a leading 0 for a Pakistani number). The earlier check was a loose pattern that rejected valid numbers with hidden characters and accepted impossible ones. The web has a `PhoneInput` (country picker with Pakistan first, as-you-type formatting, a pasted +number switches the country, a message that names the country and gives an example). Landlines are refused because the numbers are used for SMS and calls. Firebase reCAPTCHA: one invisible verifier per page element, created once and reused for every send; a failed send resets its widget (`grecaptcha.reset`) instead of making another; a double click joins the send in flight; the verifier is rebuilt only if its element was replaced and is disposed when the panel closes. This replaces the first fix (clear and recreate on every send), which still produced "already been rendered".
